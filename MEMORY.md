## Key Decisions

- Pocket Chief is a private, single-user PWA, not a public reference site.
- Authentication uses passwordless email OTP and an allowlisted owner email.
- The primary experience is search and browse; chat and built-in spaced repetition are out of v1.
- Topics follow an editable SCORE hierarchy and can carry personal tags.
- AI composes flexible pages from controlled content blocks. Human approval is required before indexing.
- The visual system is Clinical Atlas: cool neutrals, one cobalt accent, compact dividers, Geist typography, and restrained motion.
- Anki exports use a reviewed cloze card with the relevant section, nearest diagram, and a Pocket Chief deep link.
- Pocket Chief never accepts PHI or patient-specific information.

- The sign-in flow is a **magic link, not a typed OTP code**, and the distinction matters for dashboard setup. `sign-in-form.tsx` calls `signInWithOtp({ shouldCreateUser: false, emailRedirectTo: origin + "/auth/callback" })`, and `auth/callback/route.ts` reads a `?code=` param and calls `exchangeCodeForSession` — the PKCE flow `@supabase/ssr`'s `createBrowserClient` uses by default. There is no field anywhere in the UI to enter a 6-digit code. So the Magic Link email template must keep `{{ .ConfirmationURL }}`; switching it to `{{ .Token }}` would send a code with nowhere to type it. Supabase has no "passwordless" toggle — passwordless is just the Email provider with the password path unused.
- Two dashboard steps that are easy to miss and both fail confusingly: **Authentication → URL Configuration** must carry the deploy origin as Site URL plus `<origin>/auth/callback` in the redirect allowlist, or the email arrives and the link dead-ends; and the **`owner_allowlist` insert must come before the invite**, not after. `pocket_chief_owner_only_signup` is a `before insert on auth.users` trigger (202608120001) that raises `Pocket Chief signup is restricted to its configured owner` for any email not already in `public.owner_allowlist`, so inviting first fails at the dashboard with that message. Correct order: insert the allowlist row → invite the owner → test sign-in. Testing before the user exists also fails, with the same generic "Sign-in was not accepted" message a non-owner rejection produces, because `shouldCreateUser: false`. Disabling public signup does not block the owner — signup governs account creation, not authentication of an existing user.

- **Do not infer Vercel env state from `demo: false` or from bare bundle greps.** Two false positives cost real time here. `isDemoMode()` is false for *both* `supabase` and `misconfigured`, so a rendered sign-in page proves nothing about configuration. - 2026-08-16 **Pocket Chief is live with all 17 topics.** Owner signed in, `installLibrary` reported 17 installed, and Postgres holds 17 topics / 17 approved versions / 7 sources / 13 taxonomy nodes. The launch sequence is finished; what remains is the phone install and polish.
- **`ensure_launch_topic` could never have worked against hosted Supabase.** It failed with `function digest(bytea, unknown) does not exist` on every authenticated request. `digest()` is pgcrypto, Supabase installs extensions into the `extensions` schema, and the function is `SECURITY DEFINER set search_path = public` — so the bare `digest(...)` in the release-digest check was unresolvable. Fixed by `20260816205528_launch_topic_search_path.sql`, which recreates the function with `set search_path = public, extensions` (202608130001 is applied and immutable). This is the archetype of the risk already recorded here: it is the one path that only executes against a real project with a signed-in owner, which was the single step never verified before deploy. **Any new SECURITY DEFINER function that calls a pgcrypto/uuid-ossp helper needs `extensions` on its search_path.**
- The seed failing is **not fatal** — `SupabaseRepository.create()` catches it, logs, and resets `launchTopicSeedAttempt` so it retries. And `installLibrary` never touches `digest`: it replays all 17 topics through `createTopicDraft` → `approveDraft`. So `POST /api/library/install` populates the whole library even while the pinned seed is broken, which is how the library landed before the migration was written.
- The pinned launch digest now lives in two migrations, because immutability forces each recreation to copy it forward. `content-contract.test.ts` used to read `202608130001` by name, which would have let a stale pin in the newest — the live one — pass unnoticed; it now scans every migration and asserts all pins match.

- 2026-08-16 the PWA had **never cached anything**. `sw.js` called `response.clone()` inside the `caches.open(...)` callback, which resolves a microtask after `return response` has handed the body to the page — so every cacheable GET threw `Failed to execute 'clone' on 'Response': Response body is already used` (96 console errors in one session) and no `cache.put` ever ran. The clone must be taken synchronously, with `event.waitUntil` holding the worker open for the write. Caches were also bumped to `v2`: the shell precache uses `cache.addAll` on `/`, `/topics`, `/saved`, and `fetch` follows redirects, so any install during the unconfigured or signed-out eras stored the "Pocket Chief is locked" or sign-in page under those keys — exactly what an offline launch would serve. The `activate` handler deletes any `pocket-chief-*` cache outside the current pair, so renaming is the purge.
- Vercel binds environment variables when a deployment is **created**, so adding them to the dashboard never fixes an existing deployment — a redeploy is always required. The Vercel MCP exposes deployment-protection but **no environment-variable tool**, and the CLI needs an interactive login, so env vars stay an owner-performed dashboard step.
